# Root-directory STATE runtime — source integration candidate

2026-11-07. Regular implementation branch `regular/state-directory-runtime-integration-20261107`, based on host-install PR #34. **Draft, not approved for host-registry installation.**

## Provenance and limitation

Host-install Work reported an unpublished separate branch implementing `state-directory-prepare`, `state-directory-inspect`, and a marker tying `/state` to installation/STATE IDs and filesystem backing. At the start of this work its branch and source files **were not present** among GitHub branches/commits accessible to Regular. This branch is an independent opt-in runtime integration candidate, **not** a claim that those unpublished Work marker bytes have been imported or reviewed. Reconcile the exact marker format, ownership, source heads and digest algorithm with Work's branch before selecting any installation.

## Implemented source path

- `state_contract.validate`: non-resident schema-2 installations may explicitly select **no registries** (`registries=[]`, `control_authority=null`), with no implicit remote-control grant. Existing managed configurations continue to require exactly one control registry. The unchanged strict schema-1 `zog-state-volume` default; explicit schema-2 `zog-state-directory` marker selects `storage_backend=root-directory` for a non-resident installation only. It binds configured installation/STATE IDs, filesystem UUID and PARTUUID, account profile and exact backing root `/`. The marker and installer_recorded marker digests as well as the bootstrap installation-record SHA are bound; an upgrade cannot switch backends without a separately reviewed migration.
- `state_inspect.load_configuration`: reconstructs and validates the correct canonical marker from the installed configuration, without accepting a caller-supplied marker as live authority.
- `state_inspect.assess_root_directory` and `_mount`: require an actual writable ext4/xfs root partition, unique matching UUID/PARTUUID and mount major/minor, and **no** `/state` mount or nested mount. `VerifiedState.recheck` still checks the retained directory descriptor and live backing before and after reads.
- `state_provision.prepare_directory_live`: uses the exact opt-in backend, caller's explicit matching STATE ID, and original durable preparation/marker/layout lock and publication path. It verifies the selected root filesystem, then idempotently creates `/state` itself as a root-owned `0755` directory if absent, fsyncs the root and directory entries, and safely reopens it with `O_NOFOLLOW`. Any nonempty unmarked directory or conflicting marker is rejected; it does not generate IDs, initialize a block device, mount, or touch any IAM/S3 scope. Legacy `state-prepare` remains restricted to volume-backed STATE. An interruption after `mkdir` may be retried only if the path remains empty or contains the exact same authorized marker/layout transaction.
- `cli.py`: `state-directory-prepare --state-volume-id <exact UUID>` and read-only `state-directory-inspect` use the canonical loader/inspection paths. Both require an explicitly installed, locally validated canonical configuration; **neither requires a registry or registrar signature**, and neither silently converts an existing ext4-volume configuration to directory-backed STATE.

## Tests and evidence

GitHub Actions `state-directory-runtime.yml` runs Python 3.12/3.13, normal pure tests plus `sudo` root-owned disposable filesystem regression runs; no retained Host paths are touched.

## 2026-11-08 approved simplification — no registrar, optional registry

The previous AI-proposed registrar Ed25519 signature for normal STATE metadata was withdrawn from host-install PR34 and PR35. It was not required by the approved beaconing design. Local installation is selected by the local installer/operator and checked using canonical `/etc/zog/host-install` configuration, installation-record SHA-256, marker bytes, selected filesystem topology and protected identity consumption. These local content hashes detect inconsistency and accidental substitution; **they do not independently establish malicious-tamper resistance against a root administrator**. No Command Center is required for the local Host to boot.

- In standalone non-resident mode, `bootstrap.registries=[]` and `bootstrap.control_authority=null`. `state_gate.decide` loads an existing valid identity with `standalone-local-ready` and `control_allowed=false`. The unchanged safety gate still requires STATE, correct accounts, healthy storage, matching identity, approved schemas, and absence of recovery holds. Fresh identity creation still requires an explicit local transaction.
- `non_resident.build_plan` now projects a root-directory mode with no `state.mount` service dependency and clear retained-root-filesystem caveat. The dedicated ext4 STATE plan remains unchanged. The block-device formatter rejects directory bundles before target selection or writes.
- Previously proposed remote Task C *operation* approvals and rollback-independent ledgers remain **separate protected-operation policies**. They do not authorize boot or `/state` creation. Root-control/host-deploy v3 registered-installation assumptions require a separate review before they can apply to standalone Hosts.
- With no registry configured, managed host-discover beacon preparation is not applicable; it must not fabricate a control authority or offline beacon. Future registry enrollment requires an explicit reviewed transition rather than changing existing boot trust silently.

Native registry-specific setup and protected Task C admission remain held. A standalone non-resident local installation has no need to reach host-registry for first install, reboot, or upgrade.
